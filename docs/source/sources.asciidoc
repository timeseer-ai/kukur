== Time Series Sources

Parameters common to all data sources are documented here.

```toml
[source.<name>]
type = "<the type of the source>"
query_retry_count = 0 # number of retries
query_retry_delay = 1.0 # seconds between retries as float
metadata_type = "<the type of the metadata source>"
metadata_sources = [] # names of additional metadata sources
data_query_interval_seconds = 123456 # <number of seconds>
# ...
```

Each source has a name.
When multiple sources with the same name are configured, the last configured one wins.

`type` specifies the type of the data source for this source.
Valid values are:

- `adodb`
- `arrows`
- `azure-data-explorer`
- `cratedb`
- `csv`
- `databricks-sql`
- `delta`
- `elasticsearch`
- `feather`
- `influxdb`
- `kukur`
- `oledb`
- `parquet`
- `piwebapi-af`
- `piwebapi-af-template`
- `piwebapi-da`
- `plugin`
- `postgresql`
ifdef::sources[]
- `redshift`
endif::sources[]
- `sqlite`
- `tdengine`

`type` is required.

`metadata_type` specifies the type of the metadata source for this source.

Valid values are:

- `adodb`
- `cratedb`
- `csv`
- `databricks-sql`
- `datafusion`
- `elasticsearch`
- `json`
- `kukur`
- `oledb`
- `piwebapi-da`
- `plugin`
- `postgresql`
ifdef::sources[]
- `redshift`
endif::sources[]
- `sqlite`
- `tdengine`

`metadata_type` is optional.
The `type` is used when not specified.

Additional metadata can be loaded from other sources as described in the section "Metadata Sources".
When multiple sources return an entry for the same metadata field, the source that occurs first in this list
gets priority.
Metadata returned by the source itself or by the `metadata` type configuration takes precendence over any additional sources configured here.

`query_retry_count` and `query_retry_delay` allow retrying all queries to a source in case of failure.
By default no requests will be retried.
`query_retry_delay` accepts floating point numbers,
for example `query_retry_delay = 0.5` will wait for 0.5 second after the first failure and between subsequent retries.

`data_query_interval_seconds` defines the maximum duration of the interval in which data is queried in one request.
A longer query is split in intervals of this length and later on reassembled.
This prevents query timeouts or works around a maximum number of points that can be returned by a source.

Example:

```toml
[source.sql]
type = "odbc"
connection_string = "..."
metadata_query = "..."
metadata_columns = [] # ...
data_query = "..."
data_query_interval_seconds = 86400
```

This ensures that queries will at most query for one day of data.

`data_query_interval_seconds` is optional.

== Metadata Sources

Metadata sources provide extra metadata for series in time series sources.
All time series sources that provide metadata can be used as a metadata source.
They accept the same configuration parameters as the time series source.

The optional `fields` parameter specifies which metadata fields will be used from the given source.

Possible metadata fields are:

include::{include-path}/metadata-fields.asciidoc[]

Example:

```toml
[source.noaa]
type = "influxdb"
database = "NOAA_water_database"
metadata_sources = ["noaa"]

[metadata.noaa]
type = "csv"
metadata = "examples/influxdb/noaa-metadata.csv"
fields = ["lower limit", "upper limit"]
```

Note that sources that are fast when listing all time series in the source by returning metadata in the same query,
will need to do an additional query to each of the configured metadata sources for each time series in the source.

== Quality

There is a possibility, for some types of sources, to add a quality column in the source file that represents the quality of the data point in the source, e.g. OPC quality code.

In this case a mapping needs to be provided.

Example:

```toml
[source.<name>]
quality_mapping = "example_mapping"

[quality_mapping.example_mapping]
GOOD = [192, 194, 197]

```
In this example we map the OPC quality of 192, 194 and 197 defined in the source as a good quality point in Kukur.

It is also possible to include ranges in the quality mapping.

Example:

```toml
[quality_mapping.example_mapping]
GOOD = [[192], [194, 200]]
```
In this example we map the OPC quality of 192, and the range of 194-200 defined in the source as a good quality point in Kukur.

If string values are used in the source, similar configuration can be used.

Example:

```toml
[quality_mapping.example_mapping]
GOOD = ["GoodQuality", "ExcellentQuality"]
```
In this example we map the "GoodQuality" and "ExcellentQuality" defined in the source as a good quality point in Kukur.

=== Display values

The quality mapping states which quality values of a source are good,
not what they mean.
A `display` mapping states what each quality value means to a person.

Example:

```toml
[quality_mapping.example_mapping]
GOOD = [192, 194]

[quality_mapping.example_mapping.display]
192 = "good"
194 = "very good"
```
In this example the OPC quality of 192 is shown as "good" and 194 as "very good".

The display mapping is a lookup of its own.
It can name quality values that are not good,
and not every quality value needs a display value.

```toml
[quality_mapping.example_mapping.display]
GoodQuality = "good"
BadQuality = "bad"
```

See <<Describing quality>> to replace the quality values of the data by their display values.

=== Quality values in the data

Kukur does not replace the quality values of a source.
The `quality` column of the returned data contains the quality values of the source itself,
either as `int16` for numerical status codes or as `string`.
An `int8` column contains simplified quality, as described in <<Simplifying quality>>.

The quality mapping travels along in the metadata of the Arrow schema,
in the `kukur.quality` entry.

```json
{"GOOD": [192, [194, 200]], "display": {"192": "good", "194": "very good"}}
```

The `display` entry is only present when the source configures one.
Since both TOML and JSON keys are strings,
the quality values in it are keyed by their string representation.

Sources that provide quality flags instead of status codes,
such as the PI Web API sources,
return them already simplified.
The same holds for a quality column that declares no mapping at all,
such as the one of a plugin source without a configured `quality_mapping`.
See <<Simplifying quality>>.

=== Simplifying quality

Use `kukur.quality.simplify` to reduce a quality column to good and bad.
It uses the embedded quality mapping,
so it works for every source.

```python
from kukur import Client, quality

client = Client()
data = quality.simplify(client.get_data(selector, start_date, end_date))
```

The resulting `quality` column is an `int8` column that follows the convention of Unix exit codes:
`0` means good,
non-zero means not good.
Its embedded mapping is `{"GOOD": [0]}`,
which makes calling `quality.simplify` again return the same data.

Sources that provide quality flags rather than status codes,
such as the PI Web API sources,
return a simplified quality column directly.
Calling `quality.simplify` on their data returns the same data.

Data points that have no quality value are considered bad.

NOTE: Never assume what a quality value means.
A status code of `0` is bad for most sources,
while a simplified `0` is good.
Read the `kukur.quality` metadata,
or call `quality.simplify` first.

=== Describing quality

Use `kukur.quality.describe` to replace the quality values of a column by their display values.
It uses the embedded display mapping,
as described in <<Display values>>.

```python
from kukur import Client, quality

client = Client()
data = quality.describe(client.get_data(selector, start_date, end_date))
```

The resulting `quality` column is a `string` column.
A quality value that has no display value is rendered as the quality value itself,
so no data point loses its quality information.

The embedded quality mapping is translated along with the column,
which means the result can still be simplified by `kukur.quality.simplify`.
